# Dependencies for the openWakeWord TRAINER IMAGE (docker/Dockerfile.oww.cuda) only.
#
# Named requirements.txt for the editor support that name carries, not because it
# is the repo's requirements - it sits in docker/ beside the one Dockerfile that
# COPIes it, and this header is what says which. docker/Dockerfile.mww.cuda has no
# counterpart on purpose: its three installs are order-dependent against the
# microwakeword source install, so a requirements file could not express them.
#
# Not the mww image, which installs microwakeword's own deps and pins numpy>=2
# against the numpy<2 below. Not record/ or preflight/ either - those are host uv
# environments with their own pyproject.toml, deliberately free of this stack.
#
# NOTHING HERE IS FOR RECORDING OR PLAYBACK. This image has no microphone and never
# opens one: `pyaudio` used to be listed, but the only things that import it are
# openWakeWord's examples/ (detect_from_microphone.py and friends), which nothing in
# this pipeline runs. Recording is record/record_samples.py, on the host.

# Core training dependencies
#
# scipy IS BOUNDED BECAUSE acoustics IS PINNED. `acoustics==0.2.6` below is from 2015
# and does `from scipy.special import sph_harm`, which scipy DEPRECATED in 1.15 and
# REMOVED in 1.17 (renamed sph_harm_y). Unbounded, a build in 2026 resolves 1.18 and
# openwakeword/data.py fails at import:
#
#     ImportError: cannot import name 'sph_harm' from 'scipy.special'.
#     Did you mean: 'sph_harm_y'?
#
# This did not bite the CUDA image because it was built when scipy was older, which
# is the whole problem with leaving it floating: the image works, the same Dockerfile
# rebuilt later does not, and nothing in the run tag records the difference. The
# CPU image found it because it was built fresh.
#

# ONNX -> tflite conversion, for onnx2tflite.py.
#
# Replaces the tensorflow-cpu==2.8.1 / tensorflow_probability / onnx_tf trio
# that openWakeWord's setup.py asks for in its extras. That stack never worked
# here (2.8.1 against protobuf >= 3.20) - which is why onnx2tflite.py exists -
# so it was ~500MB of dead weight in the image.
#
# `tensorflow`, NOT `tensorflow-cpu`, even though this step is CPU-only.
# onnx2tf's own requirement is `tensorflow>=2.21,<2.22`, and pip satisfies that
# with the `tensorflow` DISTRIBUTION specifically - asking for tensorflow-cpu
# gets you both, two distributions writing the same `tensorflow/` package, with
# whichever lands last winning. The plain wheel is safe here: CUDA libraries
# arrive only via the `tensorflow[and-cuda]` extra, so no nvidia-* wheels are
# pulled and nothing disturbs the ones the Dockerfile points onnxruntime-gpu's
# loader at. Verified by dry-run resolve on python:3.10-slim: no nvidia-*, and
# numpy holds at 1.26.4 under the `numpy<2` pin above.
#
# Only tensorflow is pinned, to the version proven on the training server.
# onnx2tf tracks TensorFlow releases closely and is left floating; it is checked
# by onnx2tflite.py, which scores every candidate conversion against the source
# ONNX and refuses to write a model that disagrees, so a bad combination fails
# loudly at conversion time rather than shipping.
#
# onnx2tf's HELPERS ARE LISTED EXPLICITLY, EVEN THOUGH ITS METADATA CLAIMS THEM.
#
# PyPI says onnx2tf requires onnx, sng4onnx and psutil at exact pins, so they look
# like pure duplication here. They were removed on exactly that reasoning and the
# build broke:
#
#     File "onnx2tf/utils/common_functions.py", line 8, in <module>
#         import psutil
#     ModuleNotFoundError: No module named 'psutil'
#
# Declared and installed are different things. Whatever the cause - a resolver
# outcome, a version whose metadata and imports disagree - the empirical fact is
# that onnx2tf imports psutil and pip did not put it there. Do not trim these back
# out on the strength of a `requires_dist` listing; the environment is the authority,
# and it disagreed once already.
#
# The build check below this in Dockerfile.oww.cuda is what caught it, which is precisely
# why that check exists: conversion runs AFTER a ~16 minute training run, so a
# dependency set that only resolves on paper would surface at the worst moment.
tensorflow==2.21.0
onnx2tf
onnx
onnx-graphsurgeon
sng4onnx
tf_keras
psutil
